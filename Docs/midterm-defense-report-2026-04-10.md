# Zflow 中期答辩汇报稿

> **用途**：本文件是论文答辩中期汇报的源文档，将作为 NotebookLM 输入，用于生成 15–25 页幻灯片。
> **说明**：每个 H2 章节大致对应 1–3 张幻灯片；表格、要点列表、`关键洞察`段落是为幻灯片抽取设计的。
> **数据时点**：2026-04-10。代码量、commit 数等均为该时点的实测值。

---

## 1. 项目背景与研究问题

### 1.1 信息消费的两难

互联网内容生产持续膨胀，用户信息获取却越来越被两类工具主导：

- **算法推荐流**（今日头条、Twitter For You、TikTok）：放弃订阅控制权，换取「省心」，代价是黑箱排序、无法审计、长期形成信息茧房。
- **集中式 RSS 阅读器**（Feedly、Inoreader、Readwise Reader）：保留订阅模型，但**数据被托管在第三方**，AI 增强能力被锁在订阅服务里，价格与可用性都不在用户手里。

第三条路 —— **自托管 RSS** —— 一直存在（Miniflux、FreshRSS），但它们普遍**不带 AI**，导致用户在「数据主权」和「智能增强」之间被迫二选一。

### 1.2 研究问题

> **能不能造一个既保持自托管数据主权、又能享受 LLM 内容增强的 RSS 阅读器？同时做到打分逻辑可解释、AI 调用可审计、对外服务可替换？**

这个问题包含三层挑战：

1. **架构层**：如何在不引入重型依赖（PostgreSQL、Elasticsearch、Redis）的前提下，支撑「打分 + 摘要 + 翻译 + 向量检索」四种 AI 能力？
2. **算法层**：LLM 不可避免有幻觉、有延迟、有成本；纯靠 LLM 排序会让产品变成另一个黑箱。如何把规则、启发式、LLM、向量四类信号有机融合？
3. **可解释性层**：用户为什么看到这篇文章、为什么这篇排得高？答案必须是用户可以读懂、可以调整的，而不是「模型说的」。

### 1.3 选题意义

- **理论意义**：在 LLM 时代重新审视「可解释推荐」与「分层摘要」两个经典命题，给出一个面向个人知识工作的具体落地方案。
- **工程意义**：验证 SQLite + sqlite-vec + 无 CGO Go 这套「轻量自托管 + 原生向量检索」的技术栈在生产场景的可行性。
- **社会意义**：为不愿被算法流绑架、又不愿放弃 AI 的用户提供一个开源、可审计、可自托管的替代品。

**本节要点**：算法流与集中 RSS 都有不可调和的缺陷，自托管 RSS 缺 AI；本研究的命题就是把这三者的优点拼起来。

## 2. 研究目标与系统定位

### 2.1 目标

构建一个开源、可自托管、零遥测的 RSS 阅读器 **Zflow**，集成下列 AI 能力，且每一项都做到可解释、可降级、可替换：

| 能力 | 具体形态 | 可替换的提供商 |
|---|---|---|
| **多维度打分** | Quality / Relevance / Depth / Freshness / Novelty 五维 + 加权合成 | 规则始终在线；LLM 层可选 |
| **AI 摘要** | 分层摘要（chunk → 阶段 → 聚合 + 重锚定原文） | OpenAI 兼容 / Anthropic SDK |
| **流式翻译** | 段落级 NDJSON 流式协议，逐段渲染 | 同上 |
| **向量检索** | sqlite-vec + OpenAI 兼容 embedding API | 模型可换，存储完全本地 |
| **知识简报** | 日 / 周 / 月级别按主题聚类自动生成 | 同上 |

### 2.2 技术定位（一句话）

> **Zflow = Miniflux 的轻量自托管 + Readwise 的 AI 智能 + 完整的数据主权 + 可解释的打分。**

### 2.3 非目标（明确不做）

- **不做多用户 SaaS**：单实例单用户场景为先，多用户作为后续阶段的可选扩展。
- **不做模型训练**：所有 AI 能力走推理 API，不在本地训练任何模型。
- **不做闭源商业版**：MIT 协议，零遥测，所有商业化路径只走「自托管 + 自带 Key」。
- **不做内容生产**：Zflow 是消费侧工具，不做内容创作或社交分发。

**本节要点**：明确目标 + 明确不做，避免后续答辩被问「为什么不做 X」时陷入辩护。

## 3. 系统架构总览

### 3.1 技术栈选型

| 层级 | 技术 | 关键决策依据 |
|---|---|---|
| 后端语言 | **Go 1.22 + Echo** | 并发模型适合后台调度器；编译为静态二进制方便分发 |
| 数据库 | **SQLite (modernc.org/sqlite)** | 无 CGO 依赖，单文件部署；WAL 模式支持高并发读 |
| 向量存储 | **sqlite-vec** | 与 SQLite 同进程，零网络开销；F32 1536 维原生支持 |
| 前端框架 | **React 18 + TypeScript + Vite** | 类型安全 + 现代构建链 |
| 数据获取 | **TanStack Query** | 服务端缓存、增量分页、请求去重 |
| 全局状态 | **Zustand** | 比 Redux 轻、比 Context 可控 |
| UI 组件 | **Tailwind CSS + shadcn/ui** | 设计系统一致，CSS 变量主题切换 |
| 路由 | **Wouter** | 比 React Router 小一个数量级，纯 hooks |
| 部署 | **Docker Compose + Nginx** | 一键自托管；前后端 + 数据卷统一编排 |

### 3.2 严格分层（依赖方向单向）

```
┌──────────┐    ┌─────────┐    ┌────────────┐    ┌────┐
│ handler  │ -> │ service │ -> │ repository │ -> │ db │
└──────────┘    └─────────┘    └────────────┘    └────┘
   HTTP 协议       业务编排        SQL 执行         SQLite
   无 SQL          无 HTTP         无业务规则       WAL+FK
```

- 所有依赖通过构造函数注入，**禁止全局可变状态**。
- 这层约束直接体现在代码 review 流程里：任何在 handler 写 SQL、在 service 写 HTTP 协议细节的提交都要被打回。

### 3.3 文档驱动开发

仓库根目录的 `.phrase/phases/phase-rss-llm-reader-20260225/` 是当前唯一活跃的 phase 目录，包含 `spec`、`plan`、`task`、`tech-refer`、`adr` 等文档。**任何代码改动都可追溯到一个 `taskNNN`**，task 完成后回写 `change_*` 与 `lessons.md`。这种「文档即事实来源」的工作流让答辩时的「这一行代码为什么这么写」永远有出处。

**本节要点**：技术栈是「一切为了自托管」选出来的；分层约束是写在 review 流程里的硬规则；文档驱动让代码可追溯到 spec。

## 4. 关键技术贡献

### 4.1 多维度可解释打分（创新点 1）

#### 4.1.1 设计动机

现有 RSS 阅读器的排序要么是**纯时间序**（Miniflux/FreshRSS），要么是**黑箱算法**（Feedly/Inoreader）。前者无法应对信息过载，后者无法解释「为什么这篇排第一」。Zflow 的方案是**把推荐分解成五个独立、可解释的维度**，每个维度有显式公式和权重，用户可读、可调。

#### 4.1.2 五维打分公式

| 维度 | 权重 | 计算方式 |
|---|---|---|
| **Quality 质量** | 0.33 | 18 + min(content_length/2800, 1)×30 + min(paragraphs/12, 1)×18 + (1−noise_ratio)×20 + 链接奖励 + 封面奖励 + 时间奖励 |
| **Relevance 相关性** | 0.27 | 标题-正文 token 级 Jaccard 相似度 ×38 + 标题信息量 ×10 + 正文信息量 ×22 |
| **Depth 深度** | 0.20 | 内容长度（截至 3200 字符）×24 + 段落数 ×20 + 独特 token 比 ×20 |
| **Freshness 新鲜度** | 0.08 | 阶梯衰减：≤24h→88、≤72h→74、≤1w→60、≤1mo→42、>1mo→24 |
| **Novelty 新颖性** | 0.12 | 62 + freshness×0.18 − 批内最大 Jaccard ×52 − 拥挤度 ×9（MMR 启发） |

合成：`composite = 0.33×Quality + 0.27×Relevance + 0.20×Depth + 0.08×Freshness + 0.12×Novelty`

#### 4.1.3 输入门控（Input Gate）

打分前先做内容质量分级：

- **invalid**（< 40 字符）→ composite 强制 ≤ 30
- **degraded**（< 120 字符 或 噪声词比 ≥ 12%）→ composite 强制 ≤ 70
- **valid** → 不限

噪声词来自 10 个硬编码英文词（copyright、subscribe、cookie 等），是把订阅墙、Cookie 提示、底部样板挡在高分之外的简单但有效手段。

#### 4.1.4 LLM 层作为「可选增强」而非替代

- **规则层始终在线**：每篇文章入库后立即计算所有五维分。
- **LLM 层可选**：用户在设置页开启后，LLM 会对文章给出 `{quality, depth, relevance, reasoning}` 的 JSON 评分。
- **失败回退**：LLM 调用超时、限流、Key 失效时，自动回退到规则层结果，**不影响阅读链路**。

> **关键洞察**：LLM 不是要替换规则，而是要修正规则在「语义判断」上的盲区（比如规则识别不出讽刺、识别不出文章是不是在讨论同一件事的不同侧面）。规则提供可解释的下界，LLM 提供可选的上界。

#### 4.1.5 与对手差异

| 系统 | 打分透明度 | 用户可调 | LLM 角色 |
|---|---|---|---|
| Feedly | 黑箱 | 否 | 闭源 SaaS |
| NewsBlur | 「训练」可解释 | 是（关键词/作者训练） | 无 LLM |
| **Zflow** | **公式可读** | **是（权重 + 规则可改）** | **可选增强，可降级** |

### 4.2 分层摘要对抗位置偏置（创新点 2）

#### 4.2.1 问题：长文摘要的位置偏置

vision/text LLM 在长文摘要场景下有一个被反复证实的问题：**注意力高度偏向开头**。直接把 5000 字符文章扔给 LLM，常见结果是「开头一段 + 第一个论点」被反复复述，**结尾的结论几乎被丢光**。学术界将这一现象称为 **positional bias**（参见 `Docs/ai-summary-research-review-20260322.md` 文献综述）。

#### 4.2.2 Zflow 的方案：分层 chunk → 阶段摘要 → 重锚定聚合

```
长文 (5000+ 字符)
   │
   ├─ 过滤图片/图注/样板噪音
   │
   ├─ 按 1200 字符切块 (最多 6 块)
   │
   ├─ 每块独立做阶段摘要 (LLM 调用 1)
   │
   ├─ 阶段摘要 + 原文锚点窗口 → 聚合 (LLM 调用 2)
   │
   └─ 如果聚合结果仍然过长 → 二次重写压缩 (LLM 调用 3)
```

#### 4.2.3 三个关键设计

1. **不做硬截断**：传统做法是结果超长就截到固定字符数，但这会把句子切成半句。Zflow 的做法是**走二次语义重写**：让模型读自己上一轮的输出，重新写一段更短但完整的版本。
2. **聚合时回看原文**：阶段摘要会丢失细节；最终聚合时**同时输入阶段摘要 + 原文窗口锚点**，强迫模型对结尾部分重新观察。
3. **`query_mode` 参数**：把 prompt 从「写题材模板」改为围绕「主旨、重点、结论」组织，让模型对帖子、回复、评论串、长文都能给出「扫读即懂」的摘要，而不是死板复述结构。

#### 4.2.4 双层存储：`ai_summary` 与 `display_summary`

- **`ai_summary`**：模型原始输出，作为「真相之源」持久化。
- **`display_summary`**：实际展示给用户的字段。可能是 ai_summary、可能是 RSS 原始摘要、可能是本地快速摘要 —— **取决于哪一层成功**。
- **状态字段** `ai_summary_status` / `display_summary_status` 让前端能精确显示「你看到的是模型摘要 / 快速摘要 / 原始摘要」，杜绝「后端有 bug 但前端假装成功」的伪影。

#### 4.2.5 工程教训（写进了 `tasks/lessons.md`）

> 摘要长度控制应放在**信息选择与 prompt 约束层**，不能靠最终字符截断或超短阶段摘要硬压；否则长文聚合会不可逆丢信息并产生半句收尾。

> 长文摘要聚合不要只看阶段摘要；最终聚合需要保留**原文窗口锚点**，否则模型容易只保留开头和中段，结尾结论会被压没。

**本小节要点**：长文摘要不是「调用一次 LLM」就完事；分层 + 重锚定 + 双层存储是把幻觉与位置偏置压下去的工程组合拳。

### 4.3 流式翻译协议（创新点 3）

#### 4.3.1 设计

- **接口**：`POST /api/v1/articles/{id}/translate/stream`，可选 `target_lang` 参数
- **响应格式**：NDJSON 流，事件类型 `start` / `chunk` / `done` / `error`

```json
{"type":"start","paragraphs":12}
{"type":"chunk","index":0,"original":"...","translated":"..."}
{"type":"chunk","index":1,"original":"...","translated":"..."}
{"type":"done"}
```

- **段落切分**：按 `</p>`、`</div>` 等块级边界从正文中提取段落
- **降级链**：full_content → summary → title

#### 4.3.2 为什么要流式

- **感知延迟**：长文翻译总耗时常常 10–30 秒；流式让用户在 1 秒内看到第一段译文，体感延迟降到接近零。
- **可中断**：用户切到其他文章时，流可以被取消，避免浪费 token。

#### 4.3.3 双协议适配

后端**同一套** service 接口同时支持：
- OpenAI 兼容协议（`/chat/completions`，BYOK）
- Anthropic 原生协议（`/v1/messages`）

protocol 字段在前端设置页可显式选择。设置保存时**显式校验**协议名，而不是「无效则静默回退默认值」—— 这是从一次「设置怎么保存都不生效」的 bug 里学出来的（见 `lessons.md`）。

### 4.4 sqlite-vec 向量检索（创新点 4）

#### 4.4.1 选型理由

主流向量库（Pinecone、Weaviate、Milvus）都需要独立服务进程，破坏了「单二进制 + 单数据库文件」的自托管承诺。**sqlite-vec** 是 SQLite 的一个虚拟表扩展，把向量存储和 KNN 检索内嵌到主库进程内，零网络开销，跟 Zflow 的整体哲学完美契合。

#### 4.4.2 当前用法

- **Embedding 模型**：默认 `text-embedding-3-small`（1536 维 float32），可配置为任何 OpenAI 兼容服务
- **批量处理**：每次最多 20 篇，文章正文截至 8000 字符
- **后台调度**：每 5 分钟扫描一次未生成 embedding 的文章并补齐
- **检索接口**：`SearchSimilar(sourceType, queryEmbedding, limit)`，返回 score = 1 − distance；按 K×3 over-fetch 来抵消类型过滤的丢失

#### 4.4.3 当前消费方
- **知识简报（Briefs）**：日 / 周 / 月级别按主题聚类自动生成的内容简报
- **「Agent 主题」探索**：把相似度高的文章聚成主题块，给用户提供「同类还有这些」的入口

#### 4.4.4 计划中的下一步消费方
- **跨文章新颖性评分**：当前 Novelty 维度只在**批内** Jaccard 去重，下一步要换成「跨最近 N 篇向量相似度」，避免重复报道在不同批次里反复刷屏
- **语义级搜索**：给用户一个跨订阅源的语义检索框，而不是基于关键词的全文匹配

## 6. 关键工程教训（已沉淀到 `lessons.md` 与研究文档）

这一节用来回应「中期阶段是不是真的在做研究、有没有可信的工程过程」这个潜在质疑。每条教训都附原因和影响。

| # | 教训 | 原因 |
|---|---|---|
| 1 | 摘要长度控制必须放在「信息选择」层，不能靠字符截断 | 字符截断会切句、长文聚合会不可逆丢信息 |
| 2 | 长文摘要聚合必须保留**原文窗口锚点** | 只用阶段摘要做最终聚合，结尾结论会被压没 |
| 3 | 推荐系统消费的字段必须独立于 UI 展示字段 | 不然展示层一改，推荐算法跟着崩 |
| 4 | AI 协议设置不能静默回退默认值 | 一旦写错，用户会看到「保存成功但不生效」的伪影 |
| 5 | 摘要 prompt 不能预设输入是「标准文章」 | 生产里有帖子 / 评论串 / 混合内容；prompt 要围绕「主旨、重点、结论」 |
| 6 | AI 摘要必须标出「你看到的是哪一层」 | 否则用户分不清模型摘要、本地回退、RSS 原始摘要 |
| 7 | 启动日志只能在端口真正 bind 成功之后输出 | 否则失败会先打 `server started` 再崩，观测被骗 |
| 8 | 正文抓取的 HTTP 超时必须独立于 feed 抓取 | 共用 8 秒全局超时会让 Readability 长文必死 |

> **关键洞察**：每一条教训都对应一次 bug 或一次踩坑，每一次都回写到 `lessons.md` 或 `Docs/` 综述里 —— 这是「文档驱动开发」工作流的具体兑现，也是中期阶段「真实工作」的可验证证据。

## 9. 风险与开放问题

### 9.1 已知风险

| 风险 | 影响 | 当前缓解 |
|---|---|---|
| **LLM 成本失控** | 用户接入按量计费 API 后可能产生意外账单 | 输入长度做了硬上限（3000/8000/1200），但缺乏可视化面板 |
| **多用户场景下的 SQLite 性能** | 单实例写入并发受限 | 当前定位是单用户；多用户作为可选扩展 |
| **向量检索的语义对齐** | 模型「认为相似」可能不等于用户「认为相似」 | 还没有用户反馈循环；Phase 2 要补 |
| **主题聚类质量** | 聚类好不好没有客观指标 | Phase 2 计划用人工标注集做评估 |

### 9.2 学术答辩可能的提问与准备方向

| 可能问题 | 准备方向 |
|---|---|
| 「为什么不直接用 PostgreSQL + pgvector？」 | 自托管的「单二进制 + 零外部依赖」诉求；性能瓶颈不在向量库 |
| 「打分公式的权重为什么是这几个数？」 | 启发式 + 后续要做用户反馈循环；权重作为可调参数暴露 |
| 「LLM 摘要怎么评估质量？」 | 当前依赖人工抽检 + 文献指标（ROUGE/BERTScore 仍在调研）；Phase 2 计划补客观评估 |
| 「跟 Folo / Readwise 的本质区别是什么？」 | **数据主权 + 可解释 + BYOK** 三位一体（详见第 7 节） |
| 「测试覆盖率只有 41% 够不够？」 | 关键路径（service / handler）有覆盖；前端组件以手测为主，CI 自动化是下一步 |

## 10. 总结

### 10.1 已经验证的命题

1. **轻量自托管 + 完整 LLM 流水线是可行的**：Go 单二进制 + SQLite + sqlite-vec 这套技术栈在 6.5 周内支撑起了打分、摘要、翻译、向量检索四种 AI 能力，9K 行后端代码，41% 测试覆盖。
2. **可解释打分能跟 LLM 增强共存**：规则层提供可读公式与下界，LLM 层提供语义判断与上界，失败可降级 —— 用户既能享受 AI 又能审计为什么。
3. **分层摘要 + 重锚定**确实能把长文位置偏置压下去（lessons 已沉淀）。
4. **文档驱动开发**让所有代码改动都可追溯到 spec 与教训，是中期阶段「研究真实发生」的硬证据。

### 10.2 中期完成度评估

**两个视角的交叉验证**：

- **里程碑视角（8 个 M）**：完全完成 5（M0.5 / M0 / M1 / M2 / M3）、进行中 2（M4 / M6）、未开始 2（M5 / M7）。
- **功能颗粒度视角（29 项能力，详见 §5.3）**：✅ 可用 18 项 + 🚧 部分可用 3 项 + ⏳ 未开始 8 项。

**两个视角都收敛在 60–65% 的完成度区间**，符合「中期阶段」的合理预期。

剩余工作的清晰分级（详见 §5.4 与 §8.1）：

- **P0 必做（4 项，约 11–14 工作日）**：探索率真实注入、推荐解释浮窗、用户反馈闭环、画像编辑器 UI —— 这 4 项支撑论文核心论点，是终期答辩的硬门槛
- **P1 应做（4 项，约 6–8 工作日）**：PWA、token 成本面板、跨文章向量新颖性、CI 自动化 —— 这 4 项是完整度，缺一两项不阻塞
- **P2 留给 Phase 2（3 项 + 长期方向）**：API 鉴权、版本化迁移、桌面端打包等 —— 写进论文「未来工作」章节即可

**8 周排期已列在 §8.1**：W1–W4 完成 P0、W5 集中做 P1、W6–W7 写论文主体、W8 论文实验与答辩材料、W9 缓冲与终演、W10 答辩。

### 10.3 论文层面的预期贡献

- **理论贡献**：把「可解释推荐」与「分层摘要」两个经典命题在 LLM 时代重新落地，给出一个面向个人知识工作的完整方案。
- **工程贡献**：验证 SQLite + sqlite-vec + 无 CGO Go 这套「极轻自托管栈」在 AI 增强场景下的可行性，为同类项目提供参考实现。
- **开源贡献**：以 MIT 协议开放完整代码与文档（包括踩坑记录），降低后续研究者的复现成本。

### 10.4 一句话定位

> **Zflow 是给「不愿意被算法流绑架，又不愿意放弃 AI」的知识工作者准备的开源、自托管、可解释的 RSS 阅读器。**
