- 先确认当前 phase 已有 `task004/005/006` 与评分、解释、排序需求，决定不新开 phase，直接在当前 phase 上补任务与实现。

- 讨论后确定评分逻辑不应该只在接口读取时现算，而应在文章生命周期内持久化，避免每次列表查询重复重算。
- 收尾时发现 AGENTS 里写的是 `.phrase/commands/done.md`，但仓库实际存在的是 `.claude/commands/done.md`，本次按实际文件执行会话保存。

## Key Decisions
- 前端排序 MVP 先采用启发式分数而非等待 LLM 真评分落地，保持界面可用并为后端协议预留稳定字段；涉及 `frontend/src/lib/article-list.ts`、`frontend/src/components/article-list/ArticleListToolbar.tsx`、`frontend/src/pages/ReaderPage.tsx`。
- 后端评分逻辑集中放在 `backend/internal/service/article_service.go`，repository 仅负责持久化与读取，避免把业务规则塞进 SQL 层。
- `backend/internal/model/article.go` 新增 `RecommendationScores` 与 `recommendation_scores` 字段，列表和详情接口统一返回同一结构，保持前后端协议简单。
- SQLite `entries` 表采用增量迁移新增 `quality_score/relevance_score/novelty_score/composite_score` 四列，路径在 `backend/internal/repository/sqlite_feed_repository_impl.go`，保证旧库可平滑升级。
- 抓取入库和缓存刷新都要重算并持久化评分：`backend/internal/handler/feed_mutation_handlers.go`、`backend/internal/handler/server.go` 在 feed 抓取链路打分，`ArticleService.ExtractReadable` 和 `ArticleService.RefreshCache` 在正文更新后回写评分。
- 为兼容旧数据，接口读取时优先返回持久化评分；若旧行仍为 0 分，则回退到动态计算，避免直接破坏现有数据可用性。
